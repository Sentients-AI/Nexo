# Vendor Domain Design

## 1. What is a Vendor?

A Vendor is an independent seller operating within the aljebal-albeedos marketplace. A Vendor is a first-class domain entity with its own stable identity and lifecycle, independent of any user account. Vendor-team users may later belong to a Vendor, but the Vendor itself exists independently and represents the seller responsible for its own marketplace operations.

The Vendor is treated as a marketplace seller rather than a user or storefront because aljebal-albeedos is a single shared marketplace where multiple independent vendors sell through one storefront.

## 2. What Identifies a Vendor?

A Vendor should have a stable internal primary key that uniquely identifies the vendor within the system. The primary key should be generated by the database and should not change during the Vendor's lifetime.

In addition to the internal primary key, each Vendor should have a unique public slug. The slug provides a stable, human-readable identifier that can be used in URLs and other public-facing contexts.

The Vendor name is the human-readable display name of the seller. It is not used as a unique identifier because different vendors may have similar or identical names.

The proposed identity fields are:

- `id` — stable primary key.
- `slug` — unique public identifier.
- `name` — human-readable Vendor name.

The database should enforce uniqueness for the primary key and slug.

## 3. What Information Must Not Live on Vendor?

The Vendor entity should contain only information that defines the Vendor's identity, lifecycle, and core business status. Data belonging to other domains should not be stored directly on Vendor.

The following information should not live on Vendor:

- User accounts and authentication data — these belong to the user and authentication domain.
- Products — products belong to the product/catalog domain and are associated with a Vendor through an explicit relationship.
- Inventory quantities — inventory belongs to the inventory domain.
- Orders and order details — orders belong to the order domain.
- Payments, Stripe accounts, transfers, and commissions — these belong to the payment and marketplace financial domains.
- Customer information — customers are marketplace-wide identities and should not be owned by a single Vendor.
- Vendor-team roles and permissions — these belong to the authorization and user-management domain.

Keeping these concerns outside Vendor prevents the entity from becoming a large container for unrelated data and keeps the domain boundaries clear.

## 4. Vendor Lifecycle States and Transitions

The Vendor lifecycle represents whether a Vendor is allowed to operate in the marketplace.

### Proposed Lifecycle States

| State | Meaning |
|---|---|
| `pending` | The Vendor exists but has not yet been approved by the Platform Operator. |
| `approved` | The Vendor has been approved and may operate in the marketplace, subject to other required conditions. |
| `suspended` | The Vendor remains in the system but is temporarily prevented from operating. |

### Proposed Transitions

| From | To | Triggered By | Meaning |
|---|---|---|---|
| `pending` | `approved` | Platform Operator | The Vendor has been reviewed and approved. |
| `approved` | `suspended` | Platform Operator | The Vendor is temporarily prevented from operating. |
| `suspended` | `approved` | Platform Operator | The suspension has been removed and the Vendor may operate again. |

Invalid transitions must be rejected by the domain/application layer. The Vendor's current status must remain unchanged when an invalid transition is attempted.

A Vendor should not be physically deleted as part of a normal lifecycle transition. Suspension preserves the Vendor's identity and historical relationships while preventing further operation.

## 5. Who May Manage a Vendor?

Vendor lifecycle management should be performed by the Platform Operator. The Platform Operator is responsible for approving and suspending Vendors.

Vendor-team users belong to exactly one Vendor and may manage vendor-specific operational activities within their permitted scope, but they should not control the Vendor's platform-level lifecycle.

Although authentication and authorization are outside the scope of this task, the design should establish an explicit application boundary for Vendor management. Later, authorization rules can enforce that only authorized Platform Operators can execute lifecycle-changing operations.

This separation ensures that Vendor lifecycle changes are controlled by the marketplace platform rather than by individual Vendor users.

## 6. Vendor Invariants

The Vendor domain must preserve the following invariants:

- **Stable identity:** A Vendor must have a stable primary identifier that does not change during its lifetime.
- **Unique public identifier:** Each Vendor must have a unique slug.
- **Valid lifecycle:** A Vendor must always have a valid lifecycle status.
- **Valid transitions:** Vendor status changes must follow the defined lifecycle transitions. Invalid transitions must be rejected.
- **Vendor isolation:** Vendor-owned data must remain associated with the correct Vendor and must not be accessible across Vendors without an explicit platform-level reason.
- **Ownership:** A Vendor is independent of user accounts. A Vendor may have vendor-team users associated with it, while a Platform Operator does not belong to any Vendor.
- **Operating ability:** A Vendor's ability to operate must be determined by its lifecycle status and other explicitly defined marketplace conditions, rather than by an unrelated field or assumption.

## 7. Database Constraints vs Application/Domain Code

Database constraints should enforce structural rules that must always be true, while application and domain code should enforce business rules and behavior.

### Database Constraints

The database should enforce:

- Primary key uniqueness for `id`.
- Non-null constraints for required fields.
- Unique constraint for `slug`.
- Appropriate foreign key constraints when relationships to other entities are introduced.
- Valid data types for stored values.

These constraints protect data integrity even if data is written through a different application path.

### Application and Domain Code

Application and domain code should enforce:

- Valid Vendor lifecycle transitions.
- Who is allowed to perform lifecycle changes.
- Whether a Vendor is allowed to operate based on its current status.
- Business rules that require context or behavior rather than simple structural validation.

For example, the database can ensure that a Vendor has a valid stored status value, while the domain layer should determine whether a transition from `suspended` to `approved` is permitted.

Using both layers provides stronger protection: the database protects structural integrity, while the application and domain layers protect business behavior.

## 8. Meaning of Suspended and Non-Active States

A `suspended` Vendor remains a valid Vendor in the marketplace but is temporarily prevented from operating. Suspension does not remove the Vendor's identity or historical data.

A `pending` Vendor has not yet been approved by the Platform Operator and therefore cannot operate as an approved seller.

An `approved` Vendor is eligible to operate, subject to other marketplace conditions such as required payment onboarding.

A `suspended` Vendor cannot perform normal seller operations such as selling products or receiving new marketplace orders. Existing historical data and records should remain available where required for auditability and order history.

Operating ability should therefore be derived from the Vendor's lifecycle status and other explicitly defined marketplace conditions rather than from a separate `is_active` field.

## 9. Proposed Vendor Schema

The proposed Vendor schema contains only fields required for Vendor identity, lifecycle, and core platform management.

| Column | Type | Null | Default | Unique | Index | Delete Behavior | Storage |
|---|---|---|---|---|---|---|---|
| `id` | BIGINT UNSIGNED | No | Auto-generated | Yes | Primary | N/A | Hard |
| `slug` | VARCHAR(255) | No | None | Yes | Yes | N/A | Hard |
| `name` | VARCHAR(255) | No | None | No | No | N/A | Hard |
| `status` | VARCHAR(50) | No | `pending` | No | Yes | N/A | Hard |
| `created_at` | TIMESTAMP | No | Current timestamp | No | No | N/A | Hard |
| `updated_at` | TIMESTAMP | No | Current timestamp | No | No | N/A | Hard |

### Field Justification

- `id` provides a stable internal identity for the Vendor.
- `slug` provides a unique, human-readable public identifier.
- `name` stores the Vendor's display name and does not need to be unique.
- `status` stores the Vendor's lifecycle state. The proposed default is `pending` so a newly created Vendor cannot operate before approval.
- `created_at` and `updated_at` provide standard record timestamps and support auditing of changes.

The Vendor table should not use soft deletion as part of the initial lifecycle design. Vendor suspension is represented explicitly through `status`, allowing the Vendor and its historical relationships to remain identifiable.

Relationships to products, orders, users, payments, and other domains should be introduced through their respective entities rather than adding unrelated fields to Vendor.

Database constraints should enforce the primary key, required fields, and unique slug. Indexes should be added where they support lifecycle or public-identifier lookups.

## 10. ADR Decision: Tenant Naming vs Vendor Naming

The greenfield Nexo marketplace should use explicit `Vendor` terminology rather than continuing the `Tenant` naming from ADR-0002.

ADR-0002 was created for an existing live SaaS database where the `tenants` table and `Tenant` model were already used across multiple models. That historical constraint does not apply to the greenfield marketplace domain.

In aljebal-albeedos, the domain meaning is different. The system is a single marketplace with multiple independent sellers, so the correct business concept is a Vendor rather than a Tenant.

Using explicit Vendor naming makes the domain model clearer and avoids carrying SaaS multi-tenancy terminology into a marketplace architecture. Vendor is also the explicit data-isolation and ownership boundary described by the current marketplace architecture.

Therefore, the proposed design is to use `Vendor` consistently for the new marketplace domain, including the model, table, relationships, and documentation.

### Proposed ADR

This decision should be documented in a new ADR explaining the divergence from ADR-0002 and establishing `Vendor` as the marketplace domain terminology.
