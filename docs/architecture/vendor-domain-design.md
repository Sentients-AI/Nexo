# Vendor Domain Design

## 1. What is a Vendor?

A Vendor is an independent seller operating within the aljebal-albeedos marketplace. A Vendor is a first-class domain entity with its own stable identity and lifecycle, independent of any user account. Vendor-team users may later belong to a Vendor, but the Vendor itself exists independently and represents the seller responsible for its own marketplace operations.

The Vendor is treated as a marketplace seller rather than a user or storefront because aljebal-albeedos is a single shared marketplace where multiple independent vendors sell through one storefront.

## 2. What Identifies a Vendor?

A Vendor should have a stable internal primary key that uniquely identifies the vendor within the system. The primary key should be generated by the database and should not change during the Vendor's lifetime.

In addition to the internal primary key, each Vendor should have a unique public slug. The slug provides a human-readable identifier that can be used in URLs and other public-facing contexts. The slug should remain unchanged during the Vendor's normal lifecycle, including approval, suspension, and reactivation. Changes to the Vendor name should not require the slug to change.

The Vendor name is the human-readable display name of the seller. It is not used as a unique identifier because different vendors may have similar or identical names.

The proposed identity fields are:

* `id` — stable primary key.
* `slug` — unique public identifier that remains stable during the Vendor's normal lifecycle.
* `name` — human-readable Vendor name.

The database should enforce uniqueness for the primary key and slug.


## 3. What Information Must Not Live on Vendor?

The Vendor entity should contain only information that defines the Vendor's identity, lifecycle, and core business status. Data belonging to other domains should not be stored directly on Vendor.

The following information should not live on Vendor:

- User accounts and authentication data — these belong to the user and authentication domain.
- Products — products belong to the product/catalog domain and are associated with a Vendor through an explicit relationship.
- Inventory quantities — inventory belongs to the inventory domain.
- Orders and order details — orders belong to the order domain.
- Payments, Stripe accounts, transfers, and commissions — these belong to the payment and marketplace financial domains.
- Customer information — customers are marketplace-wide identities and should not be owned by a single Vendor.
- Vendor-team roles and permissions — these belong to the authorization and user-management domain.

Keeping these concerns outside Vendor prevents the entity from becoming a large container for unrelated data and keeps the domain boundaries clear.

## 4. Vendor Lifecycle States and Transitions

The Vendor lifecycle represents the operational state of a Vendor after a Vendor record has been created.

### Proposed Lifecycle States

| State       | Meaning                                                                                                                 |
| ----------- | ----------------------------------------------------------------------------------------------------------------------- |
| `pending`   | The Vendor record exists but has not yet been approved by the Platform Operator. The Vendor is not eligible to operate. |
| `approved`  | The Vendor has been approved and is eligible to operate, subject to other required marketplace conditions.              |
| `suspended` | The Vendor remains in the system but is temporarily prevented from operating.                                           |

These three states are sufficient to represent the Vendor's operational lifecycle:

* `pending` represents a Vendor that exists but has not yet received platform approval.
* `approved` represents a Vendor that has received approval and may operate when other required conditions are satisfied.
* `suspended` represents a previously approved Vendor that is temporarily prevented from operating.

A rejected application is not represented as a separate Vendor lifecycle state. Rejection is an onboarding/application outcome rather than an operational state of an active Vendor. The application may be rejected without allowing the prospective seller to become an approved Vendor. If the marketplace later requires persistent application history, that outcome should be represented in the onboarding/application domain rather than adding another Vendor lifecycle state.

### Proposed Transitions

| From        | To          | Triggered By      | Meaning                                                           |
| ----------- | ----------- | ----------------- | ----------------------------------------------------------------- |
| `pending`   | `approved`  | Platform Operator | The Vendor has been reviewed and approved.                        |
| `approved`  | `suspended` | Platform Operator | The Vendor is temporarily prevented from operating.               |
| `suspended` | `approved`  | Platform Operator | The suspension has been removed and the Vendor may operate again. |

Invalid transitions must be rejected by the domain/application layer. The Vendor's current status must remain unchanged when an invalid transition is attempted.

A Vendor should not be physically deleted as part of a normal lifecycle transition. Suspension preserves the Vendor's identity and historical relationships while preventing further operation.


## 5. Who May Manage a Vendor?

Vendor lifecycle management should be performed by the Platform Operator. The Platform Operator is responsible for reviewing Vendor applications, creating Vendor records, approving Vendors, and suspending Vendors.

### Vendor Creation

A prospective seller submits an application before a Vendor record exists. Submitting an application does not directly create a Vendor record.

The Platform Operator reviews the application. If the application is accepted, the Platform Operator explicitly creates the Vendor through the Vendor management boundary.

The `pending` state begins when the Vendor record is created. A newly created Vendor starts as `pending` and must then be explicitly approved through the defined lifecycle transition before it can operate.

Vendor-team users belong to exactly one Vendor and may manage vendor-specific operational activities within their permitted scope, but they should not control the Vendor's platform-level lifecycle.

Although authentication and authorization are outside the scope of this task, the design should establish an explicit application boundary for Vendor management. Later, authorization rules can enforce that only authorized Platform Operators can execute lifecycle-changing operations.

This separation ensures that Vendor lifecycle changes are controlled by the marketplace platform rather than by individual Vendor users.

## 6. Vendor Invariants

The Vendor domain must preserve the following invariants:

- **Stable identity:** A Vendor must have a stable primary identifier that does not change during its lifetime.
- **Unique public identifier:** Each Vendor must have a unique slug.
- **Valid lifecycle:** A Vendor must always have a valid lifecycle status.
- **Valid transitions:** Vendor status changes must follow the defined lifecycle transitions. Invalid transitions must be rejected.
- **Vendor isolation:** Vendor-owned data must remain associated with the correct Vendor and must not be accessible across Vendors without an explicit platform-level reason.
- **Ownership:** A Vendor is independent of user accounts. A Vendor may have vendor-team users associated with it, while a Platform Operator does not belong to any Vendor.
-  **Operating eligibility:** A Vendor with `pending` or `suspended` status is not eligible to operate. An `approved` status is required but is not necessarily sufficient for operation; any additional marketplace conditions required for operation must also be satisfied.

## 7. Database Constraints vs Application/Domain Code

Database constraints should enforce structural rules that must always be true, while application and domain code should enforce business rules and behavior.

### Database Constraints

The database should enforce:

* Primary key uniqueness for `id`.
* Non-null constraints for required fields.
* Unique constraint for `slug`.
* A constraint on `status` that permits only the defined lifecycle values: `pending`, `approved`, and `suspended`.
* Appropriate foreign key constraints when relationships to other entities are introduced.
* Valid data types for stored values.

These constraints protect data integrity even if data is written through a different application path.

The database constraint on `status` prevents invalid lifecycle values from being stored. The exact database mechanism, such as a `CHECK` constraint or an equivalent database-supported constraint, may depend on the selected database technology.

### Application and Domain Code

Application and domain code should enforce:

* Valid Vendor lifecycle transitions.
* Who is allowed to perform lifecycle changes.
* Whether a Vendor is allowed to operate based on its current status and other required marketplace conditions.
* Business rules that require context or behavior rather than simple structural validation.

For example, the database can ensure that `status` contains only a defined lifecycle value, while the domain layer determines whether a transition from `suspended` to `approved` is permitted.

Using both layers provides stronger protection: the database protects structural integrity, while the application and domain layers protect business behavior.


## 8. Meaning of Suspended and Non-Active States

A `suspended` Vendor remains a valid Vendor in the marketplace but is temporarily prevented from starting new marketplace activity. Suspension does not remove the Vendor's identity or historical data.

A `pending` Vendor has not yet been approved by the Platform Operator and therefore cannot operate as an approved seller.

An `approved` Vendor is eligible to operate, subject to other marketplace conditions such as required payment onboarding.

### Suspended Vendor Permissions

A suspended Vendor remains able to access historical information and complete existing operational obligations, but cannot perform new selling activities.

| Action | Suspended Vendor |
|---|---|
| View historical orders | Allowed |
| Fulfill existing orders | Allowed |
| View historical earnings | Allowed |
| Edit existing products | Blocked |
| Create new products | Blocked |
| Receive new orders | Blocked |

A suspended Vendor remains identifiable and its historical records are preserved. Suspension blocks new marketplace activity without removing existing historical data or obligations.

Operating ability should therefore be derived from the Vendor's lifecycle status and other explicitly defined marketplace conditions rather than from a separate `is_active` field.
## 9. Proposed Vendor Schema

The proposed Vendor schema contains only fields required for Vendor identity, lifecycle, and core platform management.

| Column       | Type            | Null | Default           | Unique | Index   | Delete Behavior | Storage    |
| ------------ | --------------- | ---- | ----------------- | ------ | ------- | --------------- | ---------- |
| `id`         | BIGINT UNSIGNED | No   | Auto-generated    | Yes    | Primary | N/A             | Persistent |
| `slug`       | VARCHAR(255)    | No   | None              | Yes    | Yes     | N/A             | Persistent |
| `name`       | VARCHAR(255)    | No   | None              | No     | No      | N/A             | Persistent |
| `status`     | VARCHAR(50)     | No   | `pending`         | No     | Yes     | N/A             | Persistent |
| `created_at` | TIMESTAMP       | No   | Current timestamp | No     | No      | N/A             | Persistent |
| `updated_at` | TIMESTAMP       | No   | Current timestamp | No     | No      | N/A             | Persistent |

### Field Justification

* `id` provides a stable internal identity for the Vendor.
* `slug` provides a unique, human-readable public identifier.
* `name` stores the Vendor's display name and does not need to be unique.
* `status` stores the Vendor's lifecycle state. The proposed default is `pending` so a newly created Vendor cannot operate before approval.
* `created_at` and `updated_at` provide standard record timestamps and support auditing of changes.

The Vendor table should not use soft deletion as part of the initial lifecycle design. Vendor suspension is represented explicitly through `status`, rather than by deleting or hiding the Vendor record.

A Vendor should not be physically deleted as part of its normal lifecycle. If deletion is ever required for an administrative or legal reason, it must be treated as a separate data-management decision and must account for the Vendor's historical relationships and referential integrity. Deletion is therefore not a Vendor lifecycle transition.

Relationships to products, orders, users, payments, and other domains should be introduced through their respective entities rather than adding unrelated fields to Vendor.

Database constraints should enforce the primary key, required fields, unique slug, and valid lifecycle status. Indexes should be added where they support lifecycle or public-identifier lookups.


## 10. ADR Decision: Tenant Naming vs Vendor Naming

The greenfield Nexo marketplace should use explicit `Vendor` terminology rather than continuing the `Tenant` naming from ADR-0002.

ADR-0002 was created for an existing live SaaS database where the `tenants` table and `Tenant` model were already used across multiple models. That historical constraint does not apply to the greenfield marketplace domain.

In aljebal-albeedos, the domain meaning is different. The system is a single marketplace with multiple independent sellers, so the correct business concept is a Vendor rather than a Tenant.

Using explicit Vendor naming makes the domain model clearer and avoids carrying SaaS multi-tenancy terminology into a marketplace architecture. Vendor is also the explicit data-isolation and ownership boundary described by the current marketplace architecture.

Therefore, the proposed design is to use `Vendor` consistently for the new marketplace domain, including the model, table, relationships, and documentation.

### Proposed ADR

This decision should be documented in a new ADR explaining the divergence from ADR-0002 and establishing `Vendor` as the marketplace domain terminology.

## 11. Implementation status (Story #1)

Sections 1–10 are the approved design and are not changed here. This section records how Story #1 implemented it, and how #35 added audited orchestration on top.

| Concern | Implementation | Enforced by |
|---|---|---|

| Slug uniqueness | `vendors_slug_unique`. Under the column's default collation, slugs that differ only in case or accents are duplicates | The database; `CreateVendorTest`, `VendorCreationConcurrencyTest` |
| Valid status | `vendors_status_check` on a binary-collated column, default `pending` | The database |
| Lifecycle (§4) | `VendorLifecycle`: approve, suspend, reactivate, each a conditional update on the expected status (INV-14) | L4 (`VendorStatusWriteRule`); `VendorLifecycleTest`, `VendorLifecycleConcurrencyTest` |

| Audited operations (#35) | `RegisterVendor`, `ApproveVendor`, `SuspendVendor`, `ReactivateVendor` in `Vendors\Application`: each change and its `audit_log` record commit or roll back together (INV-19, ADR-0023) | L9 (`VendorOrchestrationRule`); `RegisterVendorTest`, `AuditedLifecycleTest`, `AuditedVendorRetryTest`, `AuditedVendorConcurrencyTest` |

### Creation rules (#29, owner decisions D1, D2)

- The operator supplies the slug: lowercase ASCII kebab-case, 3–80 characters, with no leading, trailing or consecutive hyphens. It is stored exactly as given.
- The name is trimmed, must be valid UTF-8, and is 1–255 characters.
- An invalid name or slug throws `InvalidVendorDetails`, which names the field but never the value.
- An equivalent slug already in use throws `VendorSlugAlreadyExists`. Only a violation of `vendors_slug_unique` is translated; every other database error propagates. There is no lookup before the insert, so two concurrent creations of one slug cannot both succeed.
- `vendors:create` exits 0 on success, 2 for an invalid slug or name, and 1 for a duplicate slug or a refused production confirmation.

### Audited operations (#35)

- **The four operations.** `RegisterVendor::handle(Actor, name, slug): Vendor` and `ApproveVendor`, `SuspendVendor` and `ReactivateVendor`, each `handle(Actor, int $vendorId): Vendor`. They reuse `CreateVendor` and `VendorLifecycle` unchanged: validation, the duplicate-slug translation, the guarded conditional updates and their exceptions are theirs.
- **Audit records.** Subject type `vendor`, subject id the Vendor's id.

  | Operation | Action | `before` | `after` |
  |---|---|---|---|
  | Register | `vendor.created` | SQL NULL | `{slug, name, status}` |
  | Approve | `vendor.approved` | `{status: pending}` | `{status: approved}` |
  | Suspend | `vendor.suspended` | `{status: approved}` | `{status: suspended}` |
  | Reactivate | `vendor.reactivated` | `{status: suspended}` | `{status: approved}` |

  The vocabulary was chosen by the owner for #35. Snapshots are explicit, minimal attribute maps, never a serialised model.
- **Authoritative snapshots (ADR-0023 amendment B).** A lifecycle orchestrator takes a Vendor id, never a caller's model. Inside its transaction it loads the row with `lockForUpdate()`, takes `before` from it, calls the lifecycle, and reads `after` from the row as written. `RegisterVendor` reads `after` back from the inserted row. The audit insert comes last (ADR-0011 lock order).
- **Transactions (ADR-0011 Decision 10).** Each runs `DB::transaction(..., 3)` on the default connection, which the recorder also uses.
  - As the outermost transaction, it owns the transaction and retries a deadlock (1213) or lock-wait timeout (1205) up to three attempts in all. Each attempt reloads and relocks the row, builds a new model and new snapshots, and reuses nothing from a failed attempt.
  - Inside a caller's transaction it runs in a savepoint and does not retry. The concurrency error propagates to the caller as `DeadlockException`, and the owner of the outermost transaction handles it and retries. Laravel attempts to roll back the savepoint, but a real MySQL deadlock (1213) has already rolled back the entire transaction, so the savepoint rollback is no guarantee that the caller's transaction is still usable.
  - Domain refusals (`InvalidVendorDetails`, `VendorSlugAlreadyExists`, `InvalidVendorTransition`, a missing Vendor) and other errors are never retried. An audit insert failure propagates and rolls the change back. Nothing outside the database happens inside the transaction.
- **Console provenance.** `vendors:create` records a `console` actor labelled `vendors:create`: which code path made the change, not who ran it (ADR-0023 Decision 2). It has no option that names a person.
- **Bypass detection.** L9 allows each protected operation only in its orchestrator's `handle()`. With L4 and L8, every status write and creation those rules can see is audited. The blind spots of all three are listed in `dependency-rules.md` §1.
- **Concurrency.** Two or four worker processes running one transition, or one registration of a slug, give exactly one success and exactly one audit record. The others are refused with the domain exception, with no exhausted retries.
- **Retry tests simulate the error, not the server.** `InjectedQueryFailure` makes a statement fail with the 1213 or 1205 error before it reaches MySQL, so the retry tests prove the orchestrators' handling of the error. They do not reproduce MySQL's server-side rollback of the whole transaction after a real deadlock. Real contention is proven by the worker processes above.

### Operating eligibility

`canOperate()` answers from the status alone, because no other marketplace condition exists yet. Approval is required but, per §6, not necessarily sufficient: a later condition is added to `Vendor::canOperate()`, which then stops being a function of status only. Nothing enforces eligibility yet, because the features it will gate (products, orders) do not exist.

### Known limitations

- **No authentication or authorisation.** The orchestrators, the primitives and `vendors:create` do not check who calls them, and accepting an `Actor` authenticates nothing. No operator identity exists: ADR-0011 was accepted on 2026-11-24 but is not implemented. Anyone who can run Artisan on a server can create a Vendor. In production the command asks for confirmation, or needs `--force`, but that is a guard against mistakes, not access control.
- **Audit covers these four operations only.** Creation and the three lifecycle transitions are audited through their orchestrators (#35). Today the only truthful actor is `console`, since no authenticated user exists. A write that bypasses L4, L8 and L9 through one of their blind spots, or raw SQL, is not audited, and the database does not enforce append-only (ADR-0021).
- **No onboarding.** Applications, rejection (REQ-VENDOR-001, 001A, draft) and the Owner membership created on approval (FR-VEN-02, draft) are not built. Task 4 follows Story #1 (#29 D7).
- **Guard blind spots.** L4, L8 and L9 see only statically known code. Their blind spots are listed in `dependency-rules.md` §1.

### Membership lock ownership (#36)

[ADR-0024](adr/0024-membership-lock-ownership-and-transaction-boundaries.md) supersedes the caller-precondition sentence in ADR-0011 Decision 10. Public application operations own their transaction boundaries and acquire the locks required by their operation.

- First-owner assignment acquires the user and vendor locks before current membership reads. Staff-role assignment acquires the same user lock before calling the transaction-bound membership port.
- Ownership transfer and reassignment acquire the vendor lock, then lock the affected active memberships in ascending ID order. Deactivation acquires the vendor and target membership locks. Staff-role assignment and deactivation coordinate through the port's locking read and the membership mutation.
- Nested callers observe the global lock order across the whole transaction. The outermost owner handles retries. Audit remains in the same transaction.

#### Membership implementation and staged isolation

- The Vendors module owns vendor_members. MySQL enforces one active membership per user and at most one active owner per vendor. The application preserves exactly one owner once assigned. Terminal deactivation retains the row. Foreign keys restrict deletion and identifier changes for referenced vendors and users.
- AssignFirstOwner creates the owner for the explicit vendor argument. TransferOwnership and ReassignOwner require an expected owner and an existing active replacement in that vendor. DeactivateMember first resolves the target within the explicit vendor and rechecks it under lock. The Identity-owned membership port checks exclusivity by user under the caller's lock.
- The operator entries are vendors:assign-first-owner and vendors:reassign-owner. Each records its command as console provenance. Production confirmation guards against accidental execution.
- The #36 criteria of gate #30 cover the schema, explicit vendor scoping, creation ownership and cross-vendor write refusals (VendorMemberTableTest, VendorMembershipTest and the no-global-scopes architecture test). The fail-closed context and context-scoped reads belong to #37. HTTP denial, scoped route bindings and controller coverage apply with the first vendor-facing HTTP surface. INV-1 remains unverified in full.
